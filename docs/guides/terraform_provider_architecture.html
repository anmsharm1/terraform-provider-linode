1. Provider architecture

Terraform does not call Linode directly. Terraform Core loads the provider executable, speaks the Terraform Plugin Protocol to it, and stores the resource state returned by the provider. This repository translates Terraform operations into calls to linodego; linodego handles HTTP requests and Linode API types.

Why the mux exists

The provider is being migrated incrementally. New managed database resources use the Plugin Framework, while legacy SDKv2 resources continue to work. main.go upgrades the SDKv2 server, creates both protocol servers, and passes them to tf6muxserver.

Where configuration becomes a client

FrameworkProvider.Configure reads provider configuration, applies defaults, initializes or reuses the Linode client, then shares provider metadata with resources and data sources.

2. Resource or data source?

Both are registered APIs, but their relationship with Terraform state differs. A resource owns a remote object's lifecycle. A data source reads an object and returns computed values; it does not create or update that object.

Terraform constructWhat Terraform asks forValkey implementation
resource "linode_database_valkey_v2"Create, refresh, update, import, and delete a managed cluster.framework_resource.go
data "linode_database_valkey_v2"Read an existing cluster by ID and expose its computed values.framework_datasource.go
data "linode_databases"List/filter database clusters across engines.linode/databases

The resource and single-instance data source share the same Model and API flattening logic. Their schemas differ: resource schema includes configuration and plan behavior; data-source schema exposes computed values plus the required ID.

3. The Valkey request path

Adding an engine is not adding a new Terraform runtime. It is adding a new package behind the provider's existing resource/data-source interfaces and using the engine-specific methods supplied by linodego.

The public contract

framework_resource_schema.go declares required identity/location fields, optional/computed engine configuration, validators, replacement rules, sensitive credentials, private networking, suspension, and snapshot outputs. Terraform validates and plans against this contract before CRUD runs.

resource "linode_database_valkey_v2" "cache" {
  label     = "cache-prod"
  region    = "us-mia"
  type      = "g7-dedicated-4-2"
  engine_id = "valkey/8.1"

  engine_config_valkey_persistence = "rdb"
}

data "linode_database_valkey_v2" "cache" {
  id = linode_database_valkey_v2.cache.id
}

framework_models.go is the translation boundary. GetEngineConfig converts known Terraform values into linodego option types; Flatten converts the API model into Terraform state. Known zero and false values are meaningful. Unknown values are not request values. For nullable fields, the model must preserve the difference between unmanaged/null and an explicit value.

4. What happens during apply

Terraform first computes a plan. At apply time it invokes the resource method selected by the planned operation. The provider performs API work, waits for asynchronous operations where required, refreshes the API object, then writes the result back to state.

Snapshot restore is discrete

available_restore_times is an API-provided inventory. A fork can use one listed timestamp or omit the timestamp to request the latest snapshot. It is not arbitrary point-in-time recovery. Persistence mode off disables backups/forks.

Suspended refresh is different

When the API reports a suspended state, the model skips SSL and credential reads and preserves known credential/certificate state. The schema marks these values sensitive, but Terraform state still needs normal protection.

5. How to add another Linode capability

Use a neighboring resource as the template, then change only what the API contract requires. Managed database packages are intentionally self-contained: registration points to constructors, the schema defines Terraform behavior, the model translates values, and resource methods orchestrate the API lifecycle.

Confirm API typesFind or add typed linodego methods; verify pointer/null semantics.
Define schemaChoose required, optional, computed, validators, sensitivity, replacement.
Implement modelFlatten responses and expand known plan values.
Implement lifecycleCall API, persist IDs, poll events/status, refresh state.
Register and verifyAdd factories, tests, docs, and dependency/build checks.

What is Valkey-specific

  • Its API client methods and engine slug, such as valkey/8.1.
  • Thirteen flat engine configuration fields, including nullable backup timing and nullable max-memory policy.
  • Discrete restore snapshots rather than an oldest-time/continuous-PITR contract.
  • Its supported update/event behavior and suspension endpoints.

What is not new: Terraform resource registration, provider metadata, typed state conversion, diagnostics, timeouts, import, and API-client use. Those follow the existing MySQL/PostgreSQL Plugin Framework patterns.

Dependency gate: A local workspace can validate an in-flight linodego change, but a mergeable provider change needs a released or approved immutable dependency version. Check the client signatures and Go version before updating go.mod; do not commit a machine-local workspace or replacement.
